# OpenCV WebLab tool expansion: primary-source research

Research date: **31 October 2026**. The existing operation registry, product brief and roadmap were reviewed alongside official OpenCV 4.13.0 documentation. The selection below is a product-fit judgment for a browser-local learning lab, not a ranking derived from adoption statistics or measured popularity.

## Assessment

Add **10 processing tools** that extend existing workflows: local contrast, regions and rectification, geometric features, fine-detail extraction and distance visualization. Each can run without model weights, an account or a processing server. The app already covers common smoothing, thresholding, gradients, basic morphology, global contrast, geometry, image combinations and object analysis; adding more variants of those basics would offer less new learning value.

The bundled runtime is pinned to **OpenCV 4.13.0** in `apps/web/public/runtime/manifest.json`. Local runtime probes during this implementation confirmed that the required APIs, including `CLAHE`, `applyColorMap`, `HoughLinesP`, `HoughCircles`, `goodFeaturesToTrack` and `distanceTransform`, are present and callable. This is stronger evidence than the existence of a tutorial, but does not establish performance or detection quality on arbitrary images. No runtime upgrade or custom build is required for this selection.

## Selected tools

| **CLAHE**                   | Adds local contrast adjustment that can be compared directly with existing global histogram equalization, especially under uneven illumination.                        | `cv.CLAHE(...).apply(...)`; grayscale input and grayscale output. | **Perspective correction**  | Introduces rectification through a visible four-corner transformation, useful for documents, signs and grids.                                                          | `cv.getPerspectiveTransform` and `cv.warpPerspective`; preserve image mode while mapping four source points to an output rectangle. [Official JavaScript guide](https://docs.opencv.org/4.13.0/dd/d52/tutorial_js_geometric_transformations.html)                    |
| **Hough line segments**     | Extends Canny and thresholding from edge pixels to detected geometry. | **Hough circles**           | Complements contour analysis with a geometric detector and exposes sensitivity to radius bounds, center spacing and accumulator thresholds.                            | `cv.HoughCircles` with `cv.HOUGH_GRADIENT`; grayscale intensity input and an RGBA annotated output. The detector performs edge processing internally. [Official JavaScript guide](https://docs.opencv.org/4.13.0/d3/de5/tutorial_js_houghcircles.html)               |
| **Top-hat**                 | Reveals small bright details relative to their surroundings and links directly to the existing opening operation.                                                      | `cv.morphologyEx` with `cv.MORPH_TOPHAT`; grayscale input and output. | **Black-hat**               | Reveals small dark details, providing a complementary experiment to top-hat under uneven backgrounds.                                                                  | `cv.morphologyEx` with `cv.MORPH_BLACKHAT`; grayscale input and output. Defined as closing minus input. [Official JavaScript guide](https://docs.opencv.org/4.13.0/d4/d76/tutorial_js_morphological_ops.html)                                                        |
| **Shi–Tomasi corners**      | Introduces local features beyond edges and external object boundaries. Quality and separation controls show why every textured pixel is not an equally useful feature. | `cv.goodFeaturesToTrack`; grayscale input, corner coordinates rendered as an RGBA marked image. | **Distance transform**      | Visualizes how far foreground pixels lie from background, adding an explanation of object interiors after segmentation.                                                | `cv.distanceTransform`; binary grayscale input. Convert the floating-point distance result into a normalized 8-bit grayscale visualization for the existing graph. [Official API reference](https://docs.opencv.org/4.13.0/d7/d1b/group__imgproc__misc.html)         |
| **Pseudocolor / color map** | Makes gradients and distance visualizations easier to inspect without requiring another analysis data type.                                                            | `cv.applyColorMap`; grayscale input, followed by BGR-to-RGBA conversion. A small palette choice can include Viridis, Cividis and Turbo. [Official API reference](https://docs.opencv.org/4.13.0/d3/d50/group__imgproc__colormap.html)                                |

CLAHE, crop/ROI, perspective correction and Hough detection were already named as possible learning improvements in `ROADMAP.md`. The other additions reuse established grayscale and visualization contracts while teaching concepts not directly exposed by the original catalog.

## Integration implications

- **Keep graph outputs as images.** Feature coordinates should initially be rendered as overlays. Structured feature tables, CSV exports and additional graph port types are separate product work. Existing connected-component and contour measurements retain their current meanings.
- **Respect the operation inputs.** Hough lines consume binary/edge images; Hough circles consume grayscale intensity images and apply Canny internally. Help text and examples should make that difference explicit. The Hough line documentation also warns that its input may be modified, so pass a copy rather than a shared cached matrix. [Line detection](https://docs.opencv.org/4.13.0/d3/de6/tutorial_js_houghlines.html), [circle detection](https://docs.opencv.org/4.13.0/d3/de5/tutorial_js_houghcircles.html)
- **Preserve reproducible geometry.** Crop and perspective coordinates need a consistent relationship to the operation's input dimensions at preview and full resolution. Document the corner order and reject empty regions or degenerate quadrilaterals. OpenCV's perspective transform requires four corresponding points and excludes collinear configurations. [Geometric transforms](https://docs.opencv.org/4.13.0/dd/d52/tutorial_js_geometric_transformations.html)
- **Scale spatial controls deliberately.** Preview scaling applies to pixel distances, radii and morphology kernels; thresholds and ratios retain their meaning. CLAHE's tile-grid dimensions are the number of tiles, rather than tile widths in pixels, and should not be multiplied by preview scale. Delete its native object after use. [CLAHE guide](https://docs.opencv.org/4.13.0/d2/d74/tutorial_js_histogram_equalization.html)
- **Label visualizations accurately.** A normalized distance image stores relative brightness rather than unmodified distance values; downstream thresholds therefore operate on the visualization. Define an explicit outcome for masks with no background pixels. Pseudocolor is a display transformation, not a physical measurement. [Distance-transform reference](https://docs.opencv.org/4.13.0/d7/d1b/group__imgproc__misc.html), [color-map reference](https://docs.opencv.org/4.13.0/d3/d50/group__imgproc__colormap.html)
- **Complete the existing integration path.** Every tool needs searchable registry metadata, parameter descriptions, worker execution, Python export, persistence compatibility and meaningful runtime tests. Native matrices, feature arrays, ROI views, transformation matrices and CLAHE instances require deterministic cleanup on success and failure.

## Deferred alternatives

**Template matching** is the strongest next candidate. `cv.matchTemplate` locates an image patch inside a larger image, and `cv.minMaxLoc` identifies a best match. However, the current engine requires equal dimensions for all two-input operations, whereas templates are usually smaller than the search image. Supporting this safely would require a separate input-dimension contract and consistent preview scaling across both sources, plus a choice between a float response visualization and an annotated best-match output. The two-input schema and Python exporter should be expanded together when this workflow is selected. [Official JavaScript guide](https://docs.opencv.org/4.13.0/d8/dd1/tutorial_js_template_matching.html)

**Watershed and GrabCut** offer richer segmentation, but their marker or foreground/background interactions are a larger teaching and interface addition than independent numeric tools. Watershed uses integer markers; GrabCut uses a region or a mask with several foreground/background states. They merit a dedicated guided workflow rather than being inserted as unexplained filters. [Watershed guide](https://docs.opencv.org/4.13.0/d2/dbd/tutorial_distance_transform.html), [GrabCut guide](https://docs.opencv.org/4.13.0/dd/dfc/tutorial_js_grabcut.html)

**Neural detectors, tracking and video processing** are outside the current product brief. Model downloads, temporal state or additional media inputs would change the app's still-image, offline learning workflow. This is a scope decision, not a claim that OpenCV cannot support them.

**More overlapping blur, threshold and gradient variants** are lower priority because the existing catalog already supports comparisons in those areas. The selection favors new capabilities that can be explained and reproduced with the present graph and export system.

## Suggested learning checks

Use controlled fixtures to distinguish the new concepts: uneven lighting for CLAHE versus global equalization; a skewed grid for perspective correction; interrupted segments and noisy circles for Hough sensitivity; small bright and dark features for top-hat versus black-hat; geometric shapes for corners and distance maps. Keep pseudocolor examples tied to the grayscale values they visualize.

Functional tests should cover channel contracts, degenerate geometry, empty detections, masks without background, preview/full-resolution behavior, input immutability and repeated execution cleanup. Compare exported Python results with the bundled runtime on deterministic images. Successful automated checks establish implementation behavior; they do not establish learner comprehension, broad detection accuracy or lower-memory-device performance.
